   - **Как реализовано:** `FavoriteRecipe` выбирает через `Pick` только `id`, `title`, `thumb`. `RecipeSearchResult` через `Omit` исключает подробные поля и добавляет `matched`. `Record` описывает подписи статусов, словари перевода ингредиентов и набор SVG-иконок.
   - **Почему так:** при изменении исходного типа производные типы обновляются вместе с ним. Это уменьшает дублирование и не даёт моделям данных незаметно разойтись.

8. **Состояние загрузки описано union-типом — ✅ выполнено**
   - **Где:** `RecipeSearchStatus` в `src/shared/types/recipe.ts` и `FavoritesPageView` в `src/pages/FavoritesPage.tsx`.

   - **Как реализовано:** строковый union не разрешает произвольную строку вместо статуса. `FavoritesPageView` разрешает только четыре корректные формы объекта: `loading`, `error`, `empty`, `ready`.
   - **Почему так:** невозможно случайно создать неизвестное состояние вроде `loadng`. Для каждого состояния TypeScript знает, какие дополнительные данные доступны.

9. **Есть осознанный выбор `type`/`interface`, `extends` и пересечение `&` — ✅ выполнено**
   - **Где:** `src/shared/types/recipe.ts`, `RecipeCard.tsx`, `FavoriteButton.tsx`.
   - **Что сделано:** `interface` используется для расширяемой формы объекта, а `type` — для union-типов и преобразований уже существующих типов.
   - **Как реализовано:** `RecipeDetails extends RecipeBase` добавляет подробные поля к базовому рецепту. `FavoriteButtonProps extends FavoriteRecipe` добавляет `compact`. `RecipeSearchResult` соединяет результат `Omit` с `{ matched: string[] }` через `&`.
   - **Почему так:** `extends` хорошо показывает наследование структуры объекта, а `type` удобнее для union, `Pick`, `Omit` и пересечений. Конструкции выбраны по назначению, а не случайно.

10. **Включён `strict`, nullable-значения проверяются — ✅ выполнено**
    - **Где:** `tsconfig.json`, `src/main.tsx`, `recipesApi.ts`, `favoritesApi.ts`.
    - **Что сделано:** включён строгий режим TypeScript. Значения `null` и `undefined` нельзя использовать как обычную строку или объект без предварительной проверки.
    - **Как реализовано:** корневой DOM-элемент проверяется до рендера. API-функция учитывает `meals: null`, `getRecipe` возвращает `RecipeDetails | null`, а необязательные поля рецепта имеют тип `string | null`.
    - **Почему так:** сервер или DOM действительно могут не вернуть значение. Явная проверка предотвращает ошибку вида «нельзя прочитать свойство у null» во время работы приложения.

11. **Данные API принимаются как `unknown` и проверяются без `as` — ✅ выполнено**
    - **Где:** `src/shared/lib/apiGuards.ts`, `recipesApi.ts`, `favoritesApi.ts`.
    - **Что сделано:** ответы внешнего сервера не считаются правильными автоматически. Перед созданием объекта рецепта проверяется форма ответа и тип каждого нужного поля.
    - **Как реализовано:** Axios получает данные как `unknown`. `isRecord` проверяет объект, `Array.isArray` — массив, `requireString` — обязательную строку, `nullableString` — строку или `null`. Только после этих проверок создаётся `RecipeDetails` или `FavoriteRecipe`.
    - **Почему так:** TypeScript не проверяет JSON во время выполнения. Утверждение `as RecipeDetails` лишь заставило бы компилятор поверить данным, а guard-функции реально проверяют их.

### Отлично

> Все требования предыдущих уровней выполнены.

12. **Создан свой полезный generic — ✅ выполнено**
    - **Где:** `QueryResult<T>` и `toResult<T>` в `src/app/api.ts`.
    - **Что сделано:** одна общая функция оборачивает запросы разных типов в понятный для RTK Query результат: либо данные, либо типизированная ошибка.
    - **Как реализовано:** `toResult<T>` принимает `Promise<T>` и возвращает `Promise<QueryResult<T>>`. Тип `T` подставляется автоматически: массив рецептов, один рецепт, избранное или строковый id.
    - **Почему так:** без generic пришлось бы писать почти одинаковый `try/catch` отдельно для каждого endpoint. Generic сохраняет точный тип результата и одновременно убирает дублирование.

13. **Запросы возвращают `Promise<T>`, ошибки типизированы — ✅ выполнено**
    - **Где:** `recipesApi.ts`, `favoritesApi.ts`, `src/app/api.ts`.
    - **Что сделано:** у каждой асинхронной функции явно указан результат: например, `Promise<RecipeSearchResult[]>`, `Promise<RecipeDetails | null>` или `Promise<FavoriteRecipe>`.
    - **Как реализовано:** ошибка в `catch` имеет тип `unknown`. Затем `getErrorMessage` отдельно проверяет Axios-ошибку, обычный `Error` и неизвестное значение. В RTK Query ошибка приводится к общей форме `{ message: string }`.
    - **Почему так:** любой JavaScript-код может выбросить не только объект `Error`, поэтому сразу считать ошибку известной нельзя. Проверка `unknown` делает обработку безопасной.

14. **Использованы `ReactNode` и `ComponentProps` — ✅ выполнено**
    - **Где:** `EmptyState.tsx`, `Icon.tsx`, `FavoritesPage.tsx`, `Button.tsx`, `Input.tsx`.

    - **Как реализовано:** `children?: ReactNode` разрешает передать в `EmptyState` текст, JSX или другой компонент. `ButtonProps extends ComponentProps<'button'>` наследует `disabled`, `onClick`, `aria-*` и остальные button props. `InputProps` берёт `ComponentProps<'input'>`, но через `Omit` заменяет стандартные `value` и `onChange` на собственный удобный интерфейс.
    - **Почему так:** стандартные HTML props не нужно вручную переписывать и поддерживать. Компонент остаётся совместимым с React и доступностью браузера.

15. **Discriminated union разбирается по полю-метке — ✅ выполнено**

    - **Что сделано:** состояние страницы избранного представлено union-типом, где поле `status` является общей меткой. Для каждого статуса хранится только нужная информация.
    - **Как реализовано:** `switch (view.status)` сужает тип. В ветке `error` доступно `view.message`, а в `ready` — `view.favorites`. После `switch` значение присваивается переменной типа `never`, чтобы компилятор потребовал обработать новый статус, если он появится.
    - **Почему так:** нельзя попытаться прочитать `favorites` во время загрузки или `message` в готовом состоянии. Все варианты контролируются компилятором.

    - **Где:** `tsconfig.json`, проверки массивов в `recipesApi.ts`, команды проекта в `package.json`.
    - **Что сделано:** компилятор проверяет небезопасное обращение по индексу и запрещает забытые переменные и параметры. Зависимости устанавливаются по lock-файлу, затем запускаются все проверки.

#### Намеренная ошибка для защиты

Временно добавь в любой `.ts`-файл:

```ts
const demoId: string = 123
```

Затем запусти:

```bash
npm run typecheck
```

TypeScript сообщит примерно следующее:

```text
Type 'number' is not assignable to type 'string'.
```

Объяснение: переменная обещает хранить строку, но ей присваивается число. После демонстрации строку нужно удалить.

## Что сделано — совсем коротко

Весь клиент приложения Recipe AI переведён с JavaScript на TypeScript.

TypeScript проверяет:

1. какие данные приходят в функции;
2. что функции возвращают;
3. какие props получают компоненты;
4. какую форму имеет Redux state;
5. какие данные пришли от API.

Главная цепочка проекта:

```text
JSON от сервера
    ↓
unknown — данным пока не доверяем
    ↓
guards и parsers проверяют поля
    ↓
RecipeDetails / FavoriteRecipe
    ↓
RTK Query → Redux → React-компоненты
```

1. **Весь `src` переведён на `.ts` и `.tsx`.**
2. **Включён `strict`, поэтому TypeScript не пропускает сомнительные места.**
3. **Данные API сначала имеют тип `unknown`, потому что сервер может прислать что угодно.**
4. **Типы проходят через весь проект: API → RTK Query → Redux → React.**
5. **Работа проверяется четырьмя командами: test, lint, typecheck и build.**

# Карта реализации: где находится код и почему так сделано

## 1. TypeScript подключён

**Где:**

- `package.json:11` — команда `typecheck`;
- `tsconfig.json` — настройки TypeScript.

**Почему:** Vite собирает TypeScript в JavaScript, но не выполняет полную проверку типов.

**Как сделано:** отдельно запускается:

```bash
npm run typecheck
```

**Что сказать:** «Vite отвечает за сборку, а `tsc --noEmit` — за проверку типов».

## 2. Включён строгий режим

**Где:** `tsconfig.json:10-19`.

Главные настройки:

- `strict` — включает строгую проверку;
- `noUncheckedIndexedAccess` — элемент массива может быть `undefined`;
- `noUnusedLocals` — запрещает неиспользуемые переменные;
- `noUnusedParameters` — запрещает неиспользуемые параметры;
- `noEmit` — TypeScript проверяет код, но не создаёт JavaScript-файлы.

**Почему:** простое переименование `.js` в `.ts` почти ничего не даёт. Нужны строгие правила.

**Что сказать:** «Строгий режим заставляет обработать `null`, `undefined` и неправильные аргументы до запуска программы».

## 3. Весь клиент переведён на TypeScript

**Где:** весь каталог `src`.

**Факт:** 33 клиентских модуля `.ts/.tsx`, один declaration-файл `vite-env.d.ts` и 0 файлов `.js/.jsx`.

**Почему:** если оставить часть приложения на JavaScript, в ней не будет полной проверки типов.

**Что сказать:** «Миграция полная для клиента. Express-сервер отдельно остался на JavaScript».

## 4. Создана общая модель рецепта

**Где:** `src/shared/types/recipe.ts`.

Основные типы:

- `RecipeBase` — общие поля `id`, `title`, `thumb`;
- `RecipeDetails` — полный рецепт;
- `RecipeSearchResult` — результат поиска;
- `FavoriteRecipe` — рецепт в избранном.

**Почему:** API, Redux и компоненты должны одинаково понимать структуру рецепта.

**Почему используются `Pick` и `Omit`:** они создают новый тип из уже существующего и не дают дублировать одинаковые поля.

**Что сказать:** «Если тип `id` изменится в основной модели, зависимые типы тоже обновятся».

## 5. Данные API проверяются во время выполнения

**Где:**

- `src/shared/lib/apiGuards.ts`;
- `src/features/recipes/recipesApi.ts:10-80`;
- `src/features/favorites/favoritesApi.ts:8-25`.

**Почему:** TypeScript-типы удаляются после сборки. Сервер всё равно может вернуть неправильный JSON.

**Как сделано:** Axios получает `unknown`, затем код проверяет объект и его поля.

```ts
const response = await httpClient.get<unknown>(...)
```

После проверки parser возвращает `RecipeDetails`.

**Что сказать:** «Generic Axios не проверяет JSON. Поэтому сначала `unknown`, потом runtime-проверка».

## 6. API-функции имеют понятный результат

**Где:**

- `recipesApi.ts:83-150`;
- `favoritesApi.ts:42-92`.

Примеры результатов:

- `Promise<RecipeSearchResult[]>`;
- `Promise<RecipeDetails | null>`;
- `Promise<FavoriteRecipe[]>`.

**Почему:** вызывающий код сразу знает, какие данные получит и может ли результата не быть.

**Что сказать:** «`RecipeDetails | null` показывает, что рецепт может не найтись».

## 7. RTK Query endpoints типизированы

**Где:** `src/app/api.ts:50-84`.

Пример:

```ts
builder.query<RecipeDetails | null, string>(...)
```

Первый тип — результат запроса. Второй тип — аргумент запроса.

**Почему:** сгенерированный hook знает тип `data` и не позволяет передать неправильный аргумент.

**Что сказать:** «Тип проходит от API-функции до React-компонента автоматически».

## 8. Redux store и hooks типизированы

**Где:**

- `src/app/store.ts:16-17`;
- `src/app/hooks.ts`;
- `IngredientsSlice.ts` и `searchSlice.ts`.

```ts
type RootState = ReturnType<typeof store.getState>
type AppDispatch = typeof store.dispatch
```

**Почему:** форма state берётся из настоящего store и не описывается второй раз вручную.

**Что сказать:** «Если reducers изменятся, `RootState` обновится автоматически».

## 9. Props, события и параметры маршрута типизированы

**Где:**

- `src/shared/ui/*.tsx`;
- `IngredientForm.tsx`;
- `RecipeCard.tsx`;
- `RecipePage.tsx:15-18`.

Примеры:

- props компонентов описаны через interface;
- `Button` и `Input` получают native props через `ComponentProps`;
- форма использует `FormEvent<HTMLFormElement>`;
- стили используют `CSSProperties`;
- параметр `id` из URL обрабатывается через `skipToken`.

**Почему `skipToken`:** `id` может быть `undefined`. Без `id` запрос вообще не должен отправляться.

**Что сказать:** «`id!` только скрыл бы проблему, а `skipToken` реально отменяет запрос без идентификатора».

## 10. Числовое поле проверяется до использования

**Где:**

- `src/pages/HomePage.tsx`;
- `src/shared/lib/recipeLimit.ts`;
- `tests/recipeLimit.test.js`.

Поле «Максимум рецептов» имеет `type="number"`, но браузер всё равно отдаёт `event.target.value` как строку. Поэтому состояние имеет тип `string`, а обработчик — `ChangeEvent<HTMLInputElement>`.

Функция `parseRecipeLimit` преобразует строку в число и принимает только целые значения от 1 до 20. Неправильное значение показывает ошибку и блокирует поиск.

**Что сказать:** «HTML input всегда отдаёт строку, поэтому сначала я проверяю значение и только затем использую его как число».

## 11. Все состояния страницы описаны явно

**Где:** `src/pages/FavoritesPage.tsx:12-64`.

Состояния:

- `loading`;
- `error`;
- `empty`;
- `ready`.

**Почему:** несколько отдельных boolean-флагов могут случайно дать невозможную комбинацию, например одновременно loading и error.

**Зачем `never`:** TypeScript сообщит об ошибке, если добавили новое состояние, но забыли обработать его в `switch`.

**Что сказать:** «Discriminated union делает невозможные состояния невозможными».

## 12. Aliases настроены в двух местах

**Где:**

- `tsconfig.json:22-25`;
- `vite.config.js:12-17`.

Aliases: `@`, `@shared`, `@features`.

**Почему два раза:**

- `tsconfig.json` нужен TypeScript;
- `vite.config.js` нужен сборщику Vite.

**Что сказать:** «Если настроить alias только в TypeScript, проверка может пройти, но сборка не найдёт модуль».

## 13. ESLint проверяет TypeScript

**Где:**

**Что сказать:** «Lint и typecheck не заменяют друг друга, поэтому используются оба».

# Частые вопросы преподавателя

> [!question]- Чем `unknown` отличается от `any`?
> `any` отключает проверку типов. Значение `unknown` нельзя использовать, пока код не проверит его тип.

> [!question]- Почему нельзя написать `axios.get<RecipeDetails>()`?
> Такой generic только обещает тип компилятору. Он не проверяет реальный JSON от сервера.

> [!question]- Что происходит с типами после сборки?
> Они удаляются. В браузере выполняется обычный JavaScript.

> [!question]- Зачем нужны `Pick` и `Omit`?
> Они создают новый тип из существующего: `Pick` оставляет выбранные поля, `Omit` исключает выбранные поля.

> [!question]- Почему `RootState` не написан вручную?
> Он выводится из настоящего store и поэтому не может случайно разойтись с reducers.

> [!question]- Чем отличаются lint, typecheck и build?
> Lint ищет проблемные конструкции, typecheck проверяет типы, build собирает приложение и проверяет весь граф imports.

> [!question]- Зачем нужен `skipToken`?
> Он не запускает RTK Query request, если обязательный аргумент отсутствует.

> [!question]- Зачем нужен `never` после `switch`?
> Он проверяет, что обработаны все варианты union type.
